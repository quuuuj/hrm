# 从零手写数智人事系统（八）：401 自动续期与单飞刷新实战

上一期把后端的双 Token 链路铺好了：登录发两个 httpOnly Cookie，`token` 15 分钟过期、`refreshToken` 7 天只在 `/refresh` 露面。今天看前端怎么接住这套机制——用户正在填表，Access Token 过期了，后端返回 1200，**用户不应该看到任何提示、不应该丢数据、页面不应该跳转**。

这就是"无感续期"要解决的问题。`hrm-admin/src/utils/request.js` 里的 60 行拦截器逻辑，干的事情听起来简单（401 了就去刷新），但有一个致命的细节：**如果页面上同时有 5 个请求都拿到 401，会不会同时发 5 个 `/refresh`？**答案是"不会"，靠的是一个叫"单飞"的并发控制模式。

## 动手前提

需完成第 7 期：后端 `/refresh` 端点能用、双 Cookie 已验证。本期需要前端能跑起来（`npm run serve`），浏览器 DevTools 开着看 Network 面板。

## 本期目标

Access Token 过期后，任意接口返回 1200 时自动触发一次 `/refresh`，新 token 写回 Cookie 后原请求自动重试；多个并发 401 只发一次 `/refresh`；刷新失败跳登录页。整个过程用户无感知。

## 单飞（single-flight）：并发 401 只刷新一次

先给本期唯一的术语下定义：**单飞（single-flight）**指多个并发请求触发同一个副作用操作时，只执行一次该操作，其余请求排队等待结果复用。

对应到续期场景：5 个请求同时 401，第一个请求负责调 `/refresh`，其余 4 个排队等它成功，然后一起重试——不是 5 个都各自调 `/refresh`，也不是 5 个都失败重试。

`hrm-admin/src/utils/request.js:33-34` 的两个变量是这个机制的骨架：

```javascript
let isRefreshing = false        // 刷新进行中的标志
let pendingRequests = []        // 等待刷新的请求队列
```

`isRefreshing` 是互斥锁，`pendingRequests` 是等待队列。看拦截器怎么用它（`request.js:51-84`）：

```javascript
instance.interceptors.response.use(response => {
  const res = response.data
  
  // 401/1200 → 静默刷新（排除登录和刷新接口本身）
  if ((res.code === 1200 || res.code === 401) &&
      !response.config.url.includes('/login') &&
      !response.config.url.includes('/refresh')) {
    
    const originalRequest = response.config
    
    if (!isRefreshing) {
      // 第一个 401：我负责刷新
      isRefreshing = true
      return axios.post(BASE_API + '/refresh', {}, { withCredentials: true })
        .then(refreshRes => {
          if (refreshRes.data.code === 200) {
            onRefreshed()                    // 唤醒队列里所有等待的请求
            return instance(originalRequest) // 重试原请求
          }
          toLogin()                          // 刷新失败 → 跳登录页
          return Promise.reject(res.message)
        })
        .finally(() => {
          isRefreshing = false               // 释放锁
        })
    } else {
      // 第二个及以后的 401：排队等刷新完成
      return new Promise(resolve => {
        pendingRequests.push(() => {
          resolve(instance(originalRequest))  // 刷新成功后重试
        })
      })
    }
  }
  // ... 其他错误处理
})
```

`onRefreshed()` 函数（`request.js:38-40`）极简：

```javascript
function onRefreshed() {
  pendingRequests.forEach(callback => callback())  // 依次执行队列里的重试
  pendingRequests = []                              // 清空队列
}
```

## 为什么这么设计：三个必须解决的问题

这个模式不是凭空想出来的，是三个具体问题的交点。

**问题一：并发请求会风暴式刷新。** 一个典型的列表页加载时会并发发 3-5 个请求（用户信息、菜单、列表数据、字典枚举），它们共享同一个 15 分钟的 Access Token，过期时刻也几乎相同——于是 5 个 401 在毫秒级同时到达拦截器。如果每个都独立调 `/refresh`，后端瞬间收到 5 个刷新请求，5 个新 token 写回 Cookie，最后一个覆盖前面 4 个，前 4 个请求的重试就全失败了。

`isRefreshing` 标志把这个问题变成"第一个到的负责干活，后来的排队"。队列里的请求不直接失败也不直接重试，而是包装成 `new Promise` 暂存——**Promise 的 resolve 时机被延后了**，等到 `onRefreshed()` 被调用时才触发 `instance(originalRequest)` 重试。

**问题二：/refresh 自己会 401 怎么办。** 死循环陷阱：如果 `/refresh` 端点返回 401（refreshToken 也过期了），拦截器会不会又触发一次 `/refresh`？看代码里那两行排除（`request.js:54-55`）：

```javascript
!response.config.url.includes('/login') &&
!response.config.url.includes('/refresh')
```

`/login` 和 `/refresh` 的响应**不参与**刷新逻辑——登录接口返回 401 是"密码错误"，刷新接口返回 401 是"refreshToken 过期"，这两种情况都应该直接 `toLogin()` 而不是再刷一次。少了这个排除，refreshToken 过期时会陷入无限循环：`/refresh` 401 → 触发刷新 → 又 `/refresh` → 又 401。

**问题三：HTTP 错误和业务错误都要接住。** 拦截器的第一个回调处理 `response`（HTTP 200 但业务码可能是 1200），第二个回调处理 `error`（HTTP 4xx/5xx）。后端那套"HTTP 200 + 业务码"设计（第 5 期讲过 `WebUtil.setStatus(200)`）让大部分认证失败走的是第一个分支，但**不能假设所有 401 都是业务码**——网络层错误、代理层 401、或者某些边缘情况会走 `error` 分支。

所以 `request.js:96-140` 的 `error` 分支里有一套几乎相同的逻辑：检查 `error.response.data.code === 1200 || res.status === 401`，同样的 `isRefreshing` 单飞，同样的 `pendingRequests` 队列。两个分支共享同一套状态变量，保证无论 401 从哪边来，都只有一个 `/refresh` 在飞。

## /refresh 请求的关键细节

刷新请求本身有三个刻意的设计（`request.js:60-63`）：

```javascript
axios.post(
  BASE_API + '/refresh',
  {},                              // 空 body，refreshToken 在 Cookie 里
  { withCredentials: true }        // 必须！否则浏览器不带 Cookie
)
```

**`withCredentials: true` 是命门。** axios 默认跨域不带 Cookie，这一行让浏览器把 `refreshToken`（Path=/refresh 的 Cookie）自动塞进请求头。后端 `SecurityConfig` 里 `cors.allowCredentials(true)` 配合这一侧才能工作——少了任何一边，refreshToken 都不会出现在请求里，`/refresh` 会返回 401 然后 `toLogin()`。

**空 body。** refreshToken 不在请求体里，在 Cookie 里。后端 `LoginController.refresh` 从 `request.getCookies()` 里找 `refreshToken` 字段（`LoginController.java:56-63`），不从 body 解析——这是 httpOnly Cookie 方案的天然结果，前端代码根本接触不到 token 值。

**用的是裸 axios 不是 instance。** 注意这里直接调 `axios.post` 而不是 `instance.post`——因为 `instance` 就是我们正在配置的这个 axios 实例，用它发 `/refresh` 会再次经过拦截器，万一刷新失败会再次触发刷新逻辑。裸 `axios` 绕过了拦截器，保证 `/refresh` 的响应只在这个 `.then` 里被处理。

关键点：**队列里的请求不是"先存起来再一个个发"，而是"Promise 挂起等 resolve"**。`pendingRequests.push(() => resolve(instance(originalRequest)))` 把重试逻辑包在回调里，`onRefreshed()` 一次性触发所有回调，这些回调各自的 `resolve` 让对应的 Promise 完成，原请求的 `.then` 继续走——对调用方来说，和一次正常成功的请求没区别。

## 动手验证：DevTools 看三次请求

前端启动后（`npm run serve`），打开浏览器 DevTools 的 Network 面板：

**1. 制造 Access Token 过期**

最快的办法是改后端 `JwtUtil.java:26` 的 `ACCESS_EXPIRATION` 为 `10 * 1000`（10 秒），重启后端，登录后等 10 秒再操作。或者直接在 DevTools 的 Application → Cookies 里把 `token` 的值改成一个乱码。

**2. 触发多个并发请求**

在首页（Dashboard）刷新页面——这个页面会并发发 3-4 个请求（用户信息、菜单、统计数据）。Network 面板里应该看到：

- 第一个 401 响应后，紧跟一个 `POST /refresh`；
- `/refresh` 成功后，原来的 3-4 个请求**自动重发**（新的请求条目，不是同一个请求的 retry 标记）；
- 整个过程没有跳转登录页，页面正常渲染。

**3. 验证单飞效果**

在 DevTools 的 Network 面板勾选 "Preserve log"，然后快速连续刷新页面两次——你会看到第一次刷新的 401 触发了一个 `/refresh`，第二次刷新时如果 `/refresh` 还在进行，新的 401 会排队等它完成，而不是又发一个 `/refresh`。

**4. 验证 refreshToken 过期**

在 Application → Cookies 里把 `refreshToken` 删掉或改成乱码，再触发 401——这次 `/refresh` 会返回 1200，页面应该跳转到 `/login`，并且两个 Cookie（`token` 和 `refreshToken`）都被清掉。

## 小坑提醒

- **`withCredentials` 漏写 refreshToken 就不会带**：axios 默认跨域不发送 Cookie，`/refresh` 请求里如果忘了 `{ withCredentials: true }`，后端拿不到 `refreshToken` Cookie，直接返回 1200，前端 `toLogin()`——看起来像是"刷新永远失败"，其实是 Cookie 压根没发出去。
- **`isRefreshing` 的释放必须在 `finally` 里**：如果放在 `.then` 里，`/refresh` 网络异常（不是 401 而是超时/断网）时 `isRefreshing` 永远是 `true`，后续所有请求都排队等一个永远不会来的 `onRefreshed()`，整个应用卡死。
- **队列里的 Promise 不能忘 `resolve`**：`pendingRequests.push(() => resolve(instance(originalRequest)))` 里的 `resolve` 是关键——它让挂起的 Promise 在刷新成功后完成。如果写成 `pendingRequests.push(originalRequest)` 只存配置不存 resolve，Promise 永远不会完成，调用方的 `.then` 永远不执行。
- **`/login` 和 `/refresh` 必须排除**：少了 `!url.includes('/refresh')`，refreshToken 过期时会无限循环调 `/refresh`；少了 `!url.includes('/login')`，登录失败（密码错误）也会误触发刷新——虽然刷新会成功（refreshToken 有效），但登录页的错误提示就被吞掉了。

## 小结

到这一步，认证链路的最后一公里应该清楚了：

1. **单飞刷新靠两个变量**：`isRefreshing` 是互斥锁保证只有一个 `/refresh` 在飞，`pendingRequests` 是 Promise 队列让并发 401 排队等结果。
2. **`/refresh` 请求的三个刻意设计**：裸 `axios` 绕过拦截器防递归、`withCredentials: true` 让浏览器自动带 Cookie、空 body（token 在 Cookie 不在请求体）。
3. **双分支覆盖**：`response` 分支接 HTTP 200 + 业务码 1200，`error` 分支接 HTTP 401/网络错误，两个分支共享同一套单飞状态。
4. **失败兜底是 `toLogin()`**：`/refresh` 失败（refreshToken 过期/无效）时清空队列、跳登录页，用户重新登录后新 token 生效。

认证和权限的前后端链路都打通了，下一期该看权限本身了——`per_menu`/`per_role`/`per_role_menu`/`per_staff_role` 四张表怎么配合、`@PreAuthorize` 怎么校验权限点、`v-permission` 指令怎么控制按钮显隐。RBAC 这层搞懂了，业务模块的权限管控才有依据。
