# 数智人事系统（十二）：部门树、角色授权与菜单维护

第 9 期验证权限链路时使用的是直接插入 `per_role_menu` 的 SQL 语句。本期落地对应的后台维护界面：部门层级管理、菜单与权限点配置、角色授权与员工角色分配。

## 动手前提

需完成第 9 期（RBAC 四张表与 @PreAuthorize 校验链）与第 11 期（CRUD 模式）。前端交互部分依赖第 10 期（动态路由与 v-permission）。

## 本期目标

- **部门管理**：两级部门通过 `parent_id` 表达父子关系；列表按根部门分页，按需查回关联子部门后挂载到父级下；
- **菜单管理**：目录、菜单、权限点三级通过 `level` 区分；新增时目录下挂菜单、菜单下挂权限点；支持权限点的启用与停用；
- **角色授权与员工分角色**：掌握授权对话框的回显与提交处理；两张关系表均采用“先删后插”模式更新。

## 页面与数据库表对应关系

相关表均位于 MySQL `hrm` 库中：

- 部门管理（`views/system/department`）对应 `sys_dept`；
- 菜单管理（`views/permission/menu`）对应 `per_menu`；

## 部门管理：parent_id 构建两级部门

`sys_dept` 表的 `parent_id` 字段默认值为 0，表示根部门。

系统部门结构固定为两层：根部门仅用于业务分组，四个考勤时间列留空；子部门填报具体时间并在写入时换算为总工时。根部门 `parent_id = 0`，子部门的 `parent_id` 指向对应的根部门 id。

### 分页查询与两阶段装配

分页查询实现（`DeptService.java:138`）：

```java
public ResponseDTO list(Integer current, Integer size, String name) {
    IPage<Dept> config = new Page<>(current, size);
    String searchName = (name == null) ? "" : name;
    IPage<Dept> page = this.deptMapper.listParentDept(config, searchName);
    List<Dept> parentList = page.getRecords();

    if (CollectionUtils.isEmpty(parentList)) {
        Map<String, Object> map = new HashMap<>();
        map.put("pages", page.getPages());
        map.put("total", page.getTotal());
        map.put("list", Collections.emptyList());
        return Response.success(map);
    }

    // 仅提取当前页父部门的 ID 列表
    List<Integer> parentIds = parentList.stream()
            .map(Dept::getId)
            .collect(Collectors.toList());

    // 按需仅查询当前页父部门下属的子部门
    List<Dept> subList = this.list(new LambdaQueryWrapper<Dept>()
            .in(Dept::getParentId, parentIds));

    // 按 parentId 分组
    Map<Integer, List<Dept>> subMap = subList.stream()
            .collect(Collectors.groupingBy(Dept::getParentId));

    // 组装子部门列表并防空
    for (Dept parentDept : parentList) {
        parentDept.setChildren(subMap.getOrDefault(parentDept.getId(), Collections.emptyList()));
    }

    Map<String, Object> map = new HashMap<>();
    map.put("pages", page.getPages());
    map.put("total", page.getTotal());
    map.put("list", parentList);
    return Response.success(map);
}
```

此处采用两阶段查询：先查当前页的根部门，再按根部门 id 集合批量查询子部门，最后在 Service 层内存拼装。

未对 `parent_id` 创建二级索引的原因：

- 部门表整体数据量通常在数十到数百行以内；
- 查询子部门需返回全部字段，走二级索引回表相比全表扫描并无性能优势。

### 避免单条 SQL 自连接查询的考量

不使用 `sys_dept p LEFT JOIN sys_dept s ON p.id = s.parent_id` 单条 SQL 分页的原因在于处理分页与计数的冲突：

- **结果集行数被展开**：一对多自连接后，每行对应一个子部门，结果集总行数反映的是子部门总数而非根部门数；
- **LIMIT 截断错位**：分页插件在最外层追加 `LIMIT` 时截断的是平铺行，导致单页返回的根部门数量不足，或同一根部门的子部门被跨页截断；
- **COUNT 统计失真**：分页插件生成的 `COUNT(*)` 统计展开行，导致前端分页条的 `total` 和 `pages` 无法对齐根部门数。

两阶段查询的划分：

- 第一阶段对根部门独立分页，保证分页计数与列表边界准确；
- 第二阶段使用 `WHERE parent_id IN (...)` 仅检索当前页相关的子部门，取回后在 Service 层分组挂载。

## 菜单管理：三级结构与权限点开关

`per_menu` 表中的节点分为三级：`level=0` 一级目录、`level=1` 二级菜单、`level=2` 权限点。

新增节点时根据当前行推导 `parent_id` 与 `level`（`views/permission/menu/index.vue:263`）：

```javascript
if (row.level === 0) {
  this.dialogForm.formData = { parentId: row.id, level: 1 }
} else if (row.level === 1) {
  this.dialogForm.formData = { parentId: row.id, level: 2 }
}
```

目录行上新增得到二级菜单，菜单行上新增得到权限点。新行的 `parent_id` 取当前行 id，`level` 在当前行基础上加 1。

**权限点开关**：仅 `level=2` 的行包含状态开关。该字段在两处生效：授权对话框的权限树仅加载 `status=1` 的节点（`MenuService.java:82`），鉴权 SQL 查询同样过滤 `status=1`（`MenuMapper.java:32`）。停用权限点后，新角色无法再获授该项；已获授该权限的角色在下次 Token 续期后权限被剔除，接口随即返回 1300。

## 分配权限：勾选树的回显与提交

角色管理页的“分配权限”对话框（`views/permission/role/index.vue:39`）使用三级树形控件展示权限点，配置结果持久化至 `per_role_menu` 表。

![角色管理分配权限对话框](https://cdn.jsdelivr.net/gh/quuuuj/hrm@ea52ccfd2052ad27ca925148d8216fa0cf806049/img/article/12/03-role-permission-dialog.png)

### 回显方向：仅回填叶子节点

打开对话框时，通过接口（`GET /role/menu/{id}`）获取该角色已绑定的菜单与权限 id 列表。前端逐一判断，仅将叶子节点传入 `setCheckedKeys`（`views/permission/role/index.vue:340`）：

```javascript
response.data.forEach(item => {
  if (this.$refs.tree.getNode(item.menuId)) {
    if (this.$refs.tree.getNode(item.menuId).isLeaf) {
      leafKeys.push(item.menuId)
    }
  }
})
this.$refs.tree.setCheckedKeys(leafKeys)
```

数据库中保存的是已选节点与半选祖先节点的并集。若将父节点 id 直接传入 `setCheckedKeys`，`el-tree` 会将父节点判定为完全选中，并级联勾选其下属的所有子节点，导致未授权权限点被误勾选。仅回填叶子节点，父级的半选或全选状态由组件自下而上推导，恢复原本的勾选状态。

对于已被停用的权限点，树数据中不包含该节点，`getNode` 返回空并直接跳过。

### 提交方向：合并叶子节点与半选节点

提交时取勾选节点与半选节点的并集（`views/permission/role/index.vue:362`）：

```javascript
setMenu(this.roleId,
  this.$refs.tree.getCheckedKeys().concat(this.$refs.tree.getHalfCheckedKeys()))
```

`getCheckedKeys()` 获取完全选中的节点（叶子节点及被全选的父节点），`getHalfCheckedKeys()` 获取半选的祖先节点。

包含半选节点的原因：第 9 期中前端导航菜单查询过滤 `level < 2`，后端权限点查询过滤 `level > 0`，二者均关联 `per_role_menu` 表。若仅提交叶子权限点，数据库中缺少对应目录与二级菜单行，员工登录后无法拉取到路由菜单，导致无法进入对应页面。因此必须将半选的父级目录和菜单节点一并写入。

### 持久化：先删后插

`RoleMenuService.java:36` 中的更新逻辑：

```java
@Transactional
public ResponseDTO setMenu(Integer roleId, List<Integer> menuIds) {
    remove(new QueryWrapper<RoleMenu>().eq("role_id", roleId));
    for (Integer menuId : menuIds) {
        save(new RoleMenu().setRoleId(roleId).setMenuId(menuId));
    }
    return Response.success();
}
```

先删除该角色原有关联记录，再批量写入本次提交的数据。“先删后插”具备幂等性，无需在前端比对增删差异；关系表不设 `is_deleted`，直接物理删除。

## 员工分配角色：相同更新模式

员工页的“分配角色”（`views/system/staff/index.vue:477`）使用多选框组：打开时调用 `GET /staff/role/{id}` 回显，确认时调用 `POST /staff/set/{id}`。后端 `StaffRoleService.setRole`（`StaffRoleService.java:26`）同样采用“先删后插”并添加 `@Transactional` 注解。此处不涉及树形层级，不存在半选问题。

## 动手验证

基于只读角色（`role_id=10`）和测试员工（`staff_id=9`）验证接口流程：

- **为角色配置权限**：提交目录（5）、菜单（1）、权限点（23）的组合：
  ```bash
  curl -s -X POST "http://localhost:8888/role/set/10" \
    -H "Content-Type: application/json" \
    -d "[5,1,23]" \
    -b cookies.txt
  ```
  在数据库中查看 `per_role_menu`：
  ```sql
  SELECT role_id, menu_id FROM per_role_menu WHERE role_id = 10;
  ```
  应返回三行记录，分别对应系统管理目录、员工管理菜单和新增员工权限点。

- **为员工分配角色**：
  ```bash
  curl -s -X POST "http://localhost:8888/staff/set/9" \
    -H "Content-Type: application/json" \
    -d "[10]" \
    -b cookies.txt
  ```

- **验证权限生效与权限点开关**：
  使用该员工重新登录后，可访问员工管理并调用新增接口；随后停用“新增员工”权限点（`id=23`）：
  ```bash
  curl -s -X PUT "http://localhost:8888/menu" \
    -H "Content-Type: application/json" \
    -d '{"id":23,"status":0}' \
    -b cookies.txt
  ```
  该员工再次续期或重新登录后，新增员工接口返回 1300。

## 小坑提醒

- **部门树组装避免引用比较陷阱**：避免使用 `==` 比较两个 `Integer` 类型的 id。落在 `-128~127` 范围外时会因无法命中常量池导致判断失败，应使用 `Objects.equals` 或通过 Map 进行分组映射；
- **部门列表分页与检索范围**：`total` 与 `pages` 仅统计根部门；名称检索仅针对根部门名称生效，检索子部门名称无法直接命中；
- **停用权限点不会物理清理关联关系**：`per_role_menu` 中的原有行保持保留，但因鉴权查询包含 `status=1` 过滤，停用后自动失效；重新启用后无需重新授权即可恢复。

## 小结

组织架构与权限维护模块落地要点：

- **部门管理采用两阶段装配**：`parent_id` 表达层级关系，根部门独立分页保证计数准确，子部门按需批量查回后在 Service 层拼装；
- **菜单管理通过 level 分级**：支持目录、菜单、权限点三级结构，权限点状态开关在授权树与鉴权查询两端同时过滤；
- **树形授权控件的回显与提交**：回显仅绑定叶子节点防止级联误勾，提交合并完全选中与半选节点以保留菜单层级，持久化采用“先删后插”保证幂等。
